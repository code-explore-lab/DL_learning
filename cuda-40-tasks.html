CUDA 入门 40 Task 路线图

环境：RTX 3060 Laptop 6GB / sm_86 / CUDA 13.4 工具：cupy（RawKernel 快速试错）+ torch（对比基准）+ nvcc（原生 .cu 文件） 目标：从 0 到能写优化的 GPU 算子，理解 Tensor/stride/view/内存层次

阶段总览

阶段 0：环境与 Hello（Task 1-5）

Task 1：环境自检

  • 目标：确认 torch / cupy / nvcc 三条线都能跑
  • 任务：写一个脚本分别验证 torch.cuda.is_available()、cupy 能 import、nvcc --version
  • 验收：三条全 OK，能打印出 RTX 3060
  • 提示：cupy 用 C:\Users\WK112\miniconda3\envs\cupy\python.exe 跑

Task 2：第一个 GPU Kernel

  • 目标：用 cupy RawKernel 跑一个 "hello from GPU"
  • 关键 API：cp.RawKernel、<<<grid, block>>> launch
  • 任务：写一个 kernel，每个 thread 打印自己的 threadIdx
  • 验收：看到 256 个线程各自打印
  • 坑：GPU printf 需要 kernel launch 后同步才能看到

Task 3：Grid/Block/Thread 索引计算

  • 目标：彻底搞懂一维索引公式 i = blockIdx.x * blockDim.x + threadIdx.x
  • 任务：写一个 kernel，输入 N=1,000,000，每个 thread 计算自己的全局下标，写到输出数组
  • 验收：输出数组正好是 [0, 1, 2, ..., N-1]
  • 思考：grid 大小怎么算？(N + block - 1) // block 为什么要这么写？

Task 4：Host-Device 内存拷贝

  • 目标：理解 cudaMalloc / cudaMemcpy（cupy 里就是 cp.array / .get()）
  • 任务：用 cupy 把 numpy 数组搬到 GPU，跑一个加 1 的 kernel，再搬回来对比
  • 验收：结果和 numpy 一致
  • 思考：拷贝开销占总时间多少？用事件计时测一下

Task 5：事件计时与错误检查

  • 目标：学会正确测 GPU 时间，学会检查 CUDA 错误
  • 任务：用 cp.cuda.Event() 测 Task 2 那个 kernel 的耗时（多次 warmup 后测）
  • 验收：能打印出 ms 级时间
  • 提示：不要用 time.time() 测 GPU，因为 kernel 是异步的

阶段 1：元素级算子（Task 6-12）

Task 6：Vector Add

  • 目标：经典入门算子，两个数组对应位置相加
  • 任务：写 my_add(a, b, out, n) kernel
  • 验收：和 a + b 结果一致
  • 对比：测和 cupy 自带 a + b 的速度差

Task 7：AXPY

  • 目标：y = a*x + y，标量乘加
  • 关键：理解 device 端怎么传标量参数
  • 验收：和 a*x + y 对比一致

Task 8：ReLU

  • 目标：深度学习最常用激活函数
  • 任务：out[i] = max(0, x[i])
  • 坑：GPU 上没有 std::max，用 fmaxf(0.f, x[i])

Task 9：Sigmoid

  • 目标：out = 1 / (1 + exp(-x))
  • 关键：用 __expf（快精度）和 expf（标准精度）对比速度
  • 思考：为什么快精度版本更快？什么时候不能用？

Task 10：一维 Copy / Scale

  • 目标：out = a * x，练手标量广播
  • 延伸：改成 stride 版本，跳过每隔一个元素

Task 11：二维 Elementwise（矩阵加法）

  • 目标：从一维升到二维，练二维索引
  • 关键：row = blockIdx.y * blockDim.y + threadIdx.y，col = blockIdx.x * blockDim.x + threadIdx.x
  • 任务：两个 1024×1024 矩阵相加
  • 验收：和 numpy A + B 一致

Task 12：速度对比表

  • 目标：把 Task 6-11 的手写 kernel 和 numpy / torch GPU 版本对比
  • 任务：列一个表格：算子 / 手写耗时 / numpy 耗时 / torch GPU 耗时 / 加速比
  • 思考：为什么手写的比 torch 慢？差在哪？

阶段 2：规约类算子（Task 13-18）

Task 13：Naive Sum（全局内存）

  • 目标：每个 block 算部分和，写回全局内存，CPU 再 reduce
  • 坑：这种写法性能极差，理解为什么
  • 任务：对 N=1M 数组求和

Task 14：Shared Memory 并行规约（基础版）

  • 目标：用 __shared__ 在 block 内并行规约
  • 关键 API：__shared__ float sdata[256];、__syncthreads()
  • 算法：相邻两个元素相加，log2(N) 步
  • 坑：线程分叉（warp divergence）

Task 15：树状规约优化

  • 目标：把 Task 14 的索引改成 sdata[2*tid] + sdata[2*tid+1]，减少 warp divergence
  • 对比：和 Task 14 的速度差

Task 16：Warp Shuffle 规约

  • 目标：用 __shfl_down_sync 在 warp 内规约，不用 shared memory
  • 关键 API：__shfl_down_sync(0xffffffff, val, offset)
  • 思考：warp shuffle 比 shared memory 快多少？

Task 17：多 Block 规约 + Atomic

  • 目标：跨 block 求和，用 atomicAdd 累加到全局变量
  • 关键 API：atomicAdd(&global_sum, partial_sum)
  • 坑：atomic 是串行的，为什么还要用？
  • 优化：先 per-block reduce 再 atomic，减少 atomic 次数

Task 18：Max / Min 规约

  • 目标：把 sum 规约改成 max 规约
  • 延伸：argmax（返回最大值的下标）

阶段 3：访存优化（Task 19-25）

Task 19：Coalesced vs Uncoalesced

  • 目标：直观看到访存模式对性能的影响

  • 任务：写两个 kernel：

    • coalesced：thread i 访问 a[i]（连续）
    • uncoalesced：thread i 访问 a[i*1024]（跨步）

  • 对比：速度差多少倍？

Task 20：Shared Memory Tiling 概念

  • 目标：理解为什么需要 tiling——把全局内存数据分块加载到 shared memory
  • 概念：shared memory 快但小（每个 block 几 KB），全局内存慢但大

Task 21：矩阵转置 Naive

  • 目标：写一个 naive 的矩阵转置 kernel
  • 坑：写的时候是 coalesced，读的时候不 coalesced（或者反过来）

Task 22：矩阵转置 Tiled

  • 目标：用 shared memory tiling 优化转置
  • 关键：block 加载一个 tile 到 shared memory，再写回转置位置
  • 对比：和 Task 21 的速度差
  • 延伸：怎么避免 shared memory bank conflict？

Task 23：Stride 寻址

  • 目标：在 GPU kernel 里按 stride 访问数据（非连续 tensor）
  • 任务：输入一个 shape=[4, 1024, 1024] 的 tensor，stride 不是连续的，写 kernel 按 stride 寻址
  • 关联：这就是你之前问的 Tensor stride 概念在 GPU 上的体现

Task 24：View 零拷贝验证

  • 目标：验证 GPU 上的 view 也是零拷贝
  • 任务：用 torch 创建一个 tensor，做 .t() / .view()，检查 .data_ptr() 是否变了
  • 思考：GPU view 为什么不需要写 kernel？它只是改了元信息

Task 25：Cache 行为观察

  • 目标：观察 L1/L2 cache 对访问模式的影响
  • 任务：同一个数组，分别顺序访问 vs 随机访问，测时间
  • 工具：torch 的 torch.cuda.Event 计时

阶段 4：矩阵乘法（Task 26-33）

Task 26：Naive Matmul

  • 目标：每个 thread 算 C 的一个元素 C[i][j] = sum_k A[i][k]*B[k][j]
  • 性能：预期很慢，理解为什么
  • 坑：B 矩阵访问是跳跃的，不 coalesced

Task 27：转置 B 优化访存

  • 目标：先把 B 转置成 B^T，这样访问 B^T[k][j] 就是连续的
  • 对比：和 Task 26 的速度差

Task 28：Shared Memory Tiling Matmul（基础版）

  • 目标：经典 CUDA 课程作业
  • 算法：每个 block 算一个 C 的 tile（比如 32×32），循环加载 A 和 B 的 tile 到 shared memory
  • 关键：__shared__ float As[32][32], Bs[32][32];
  • 对比：和 Task 27 的速度差

Task 29：寄存器分块

  • 目标：每个 thread 算 4×4 个输出元素，而不是 1 个
  • 好处：减少 shared memory 访问次数，增加算术密度
  • 对比：和 Task 28 的速度差

Task 30：对比 cuBLAS

  • 目标：测 torch.matmul(A, B) 的速度，和你手写的对比
  • 思考：cuBLAS 比你快多少倍？为什么？
  • 现实：手写能跑到 cuBLAS 的 50% 就已经不错了

Task 31：不同形状的性能

  • 目标：测 M=N=K=512 / 1024 / 2048 / 4096 时的性能
  • 任务：画一个表格：尺寸 / 你的 kernel GFLOPS / cuBLAS GFLOPS
  • 思考：为什么大矩阵相对性能更好？

Task 32：占用率分析

  • 目标：理解 occupancy（一个 SM 上能同时跑多少 warp）
  • 概念：block 大小、shared memory 用量、register 用量怎么影响 occupancy
  • 工具：nvcc 的 --ptxas-options=-v 看 register 用量

Task 33：Roofline 模型

  • 目标：理解你的 kernel 是 compute-bound 还是 memory-bound
  • 公式：算术强度 = 计算量 / 访存量
  • 思考：matmul 是 compute-bound，reduction 是 memory-bound，为什么？

阶段 5：工程与进阶（Task 34-40）

Task 34：Multi-Stream 并行

  • 目标：用多个 CUDA stream 重叠计算和拷贝
  • 关键 API：cp.cuda.Stream()
  • 场景：处理多个小 batch，用 stream 重叠

Task 35：Atomic Histogram

  • 目标：用 atomicAdd 实现 histogram
  • 任务：对一个 1M 数组，统计每个值出现的次数（量化到 256 个 bin）
  • 坑：atomic 冲突怎么优化？（per-block local histogram 再合并）

Task 36：Softmax Kernel

  • 目标：深度学习常用算子
  • 算法：两步规约——先找 max，再算 sum(exp(x-max))，最后归一化
  • 挑战：怎么避免数值不稳定？为什么要先减 max？

Task 37：Layer Norm Kernel

  • 目标：对每一行做归一化
  • 关联：和 softmax 的规约步骤很像

Task 38：torch C++ Extension 封装

  • 目标：把你写的某个 kernel（比如 add 或 matmul）用 torch.utils.cpp_extension.load 封装
  • 效果：Python 里直接 torch.my_add(a, b) 调用
  • 意义：这就是工业界自定义算子的标准流程

Task 39：Profile 工具入门

  • 目标：用 nsys 或 ncu 看你的 kernel 瓶颈在哪
  • 任务：对 Task 28 的 tiling matmul 跑一次 ncu，看 memory throughput / compute throughput
  • 思考：你的瓶颈是访存还是计算？

Task 40：迷你 Tensor 类

  • 目标：综合所有知识，写一个极简 Tensor 类

  • 功能：

    • GPU storage（float* data）
    • shape + stride + offset
    • view() 零拷贝（只改 shape/stride）
    • 调用你写的 add / matmul kernel

  • 意义：把前面 39 个 task 的知识点串起来——这就是你最开始问的 "Tensor 如何管理内存 / shape&stride / view 零拷贝" 的工程实现

推荐执行顺序与节奏

关键原则

  1. 先用 cupy RawKernel 快速试错，跑通了再考虑要不要用 nvcc 写 .cu 文件
  2. 每个 kernel 写完都要和 torch GPU 版本对比速度，不要闭门造车
  3. 遇到性能问题，先怀疑访存模式，再怀疑计算
  4. 手写 kernel 永远比不过 cuBLAS/cuDNN，学习目的是理解原理，不是替代框架
  5. 6GB 显存够用了，矩阵别超过 4096×4096（float32 一个矩阵 64MB）
